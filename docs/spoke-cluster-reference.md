This document covers the conceptual model behind ACM-managed spoke cluster
provisioning, prerequisites and planning inputs, how to invoke the automated
onboarding pipeline, and how to monitor, verify, and deliver GitOps workloads
to a spoke cluster after it is running.

For the step-by-step automated pipeline that builds and deploys the cluster
manifests, see [Cluster Onboarding Pipeline](cluster-onboarding-pipeline.md).

## 1. How Spoke Cluster Provisioning Works

ACM uses the Assisted Installer service (part of MultiClusterEngine) to
provision bare metal spoke clusters. The same Agent-Based Installer mechanics
used for the hub apply to spoke clusters — each node boots from a
cluster-specific discovery ISO generated by the Assisted Installer service
running on the hub, rather than by the `openshift-install` CLI.

```
vars/clusters/<name>.yml
        │
        ▼
cluster_onboard.yml (Ansible pipeline)
        │
        ├─ Validates DNS + CIDR pre-flight
        ├─ Harvests serial numbers + MACs from BMC
        ├─ Boots nodes from live ISO, collects callbacks
        ├─ Renders and commits cluster manifests to Git
        └─ Loads spoke secrets into Vault
        │
        ▼
ArgoCD (hub) detects Git change → syncs hub Application
        │
        ▼
ClusterDeployment + AgentClusterInstall + InfrastructureEnv
applied to hub cluster (in spoke namespace)
        │
        ▼
Assisted Installer (running on hub) generates
cluster-specific discovery ISO
        │
        ▼
pipeline retrieves isoDownloadURL →
BMC mounts ISO → nodes boot → agents register with ACM
        │
        ▼
Cluster installs → ACM imports cluster →
gitops-bootstrap-policy applies → spoke ArgoCD running
```

### ACM and Hive resource types

The pipeline generates these resources, all applied to the hub cluster in the
spoke's dedicated namespace:

| Resource | API Group | Purpose |
|----------|-----------|---------|
| `Namespace` | `v1` | Dedicated namespace on the hub for all spoke provisioning resources |
| `ClusterDeployment` | `hive.openshift.io/v1` | Cluster identity, base domain, install strategy, pull secret reference |
| `AgentClusterInstall` | `extensions.hive.openshift.io/v1beta1` | Network CIDRs, API/Ingress VIPs, node counts, SSH key |
| `InfrastructureEnv` | `agent-install.openshift.io/v1beta1` | Links to ClusterDeployment; triggers discovery ISO generation |
| `NMStateConfig` | `agent-install.openshift.io/v1beta1` | Per-node static network config (IP, gateway, DNS, routes, MAC binding) |
| `ExternalSecret` | `external-secrets.io/v1beta1` | Syncs pull secret from Vault as a `kubernetes.io/dockerconfigjson` Secret |
| `ManagedCluster` | `cluster.open-cluster-management.io/v1` | ACM cluster registration (created automatically by ACM on install completion) |

### Resource lifecycle

1. **ClusterDeployment + AgentClusterInstall** — ArgoCD creates these; they remain in `installed: false` state until the Assisted Installer marks installation complete.
2. **InfrastructureEnv** — Created by ArgoCD alongside ClusterDeployment. The Assisted Installer watches this resource and generates the discovery ISO, populating `status.isoDownloadURL`.
3. **NMStateConfig** — One per node. The ISO embeds these configs so each node comes up with the correct static IP at first boot, matched to the node's MAC address.
4. **Agents** — Created automatically as each node boots from the discovery ISO and registers with the Assisted Installer. When all expected agents are registered and validated, installation begins.
5. **ManagedCluster** — Created by ACM automatically when installation completes. The `gitops-bootstrap-policy` detects the new ManagedCluster and installs the OpenShift GitOps operator on it.

## 2. Prerequisites

- Hub cluster is fully running with ACM, Vault, and ESO healthy
- `AgentServiceConfig` in `components/acm-configuration/` is deployed and the `assisted-service` pod is Running:
  ```bash
  oc get agentserviceconfig agent -n multicluster-engine
  oc get pods -n multicluster-engine -l app=assisted-service
  ```
- `ClusterImageSet` for the target OCP version exists:
  ```bash
  oc get clusterimageset
  ```
  If the required version is missing, add it to `components/acm-configuration/clusterimageset.yaml` and sync ArgoCD before onboarding.
- Nodes have iDRAC/BMC reachable from the Ansible control node
- DNS entries for the new cluster are resolvable before the pipeline runs — the pre-flight check validates these:
  - `api.<cluster>.<domain>` → cluster API VIP
  - `*.apps.<cluster>.<domain>` → cluster Ingress VIP
- Pull secret and SSH public key are already loaded in Vault at the paths referenced in `cluster.pull_secret_vault_path` and `cluster.ssh_key_vault_path` (populated during hub bootstrap)

## 3. Plan the Cluster

Gather these values before creating the cluster definition file. They become
the fields in `vars/clusters/<name>.yml`.

| Setting | Example | Notes |
|---------|---------|-------|
| Cluster name | `spoke1` | Short, DNS-safe, unique across all clusters |
| Base domain | `example.com` | Must match hub or a delegated zone |
| OCP version | `4.20` | Must match an available `ClusterImageSet` |
| Node count | 3 (compact) or 3+N | 3 control-plane nodes; add workers for larger clusters |
| API VIP | `192.168.2.100` | Unused IP within `machine_network_cidr`; reserved for the API load balancer |
| Ingress VIP | `192.168.2.101` | Unused IP within `machine_network_cidr`; reserved for the Ingress load balancer |
| Machine network | `192.168.2.0/24` | Routable subnet the physical nodes live on |
| Cluster network | `10.132.0.0/14` | OVN pod CIDR — must not overlap hub or other spokes |
| Service network | `172.31.0.0/16` | OVN service CIDR — must not overlap hub or other spokes |
| MetalLB pool | `192.168.2.200–220` | Reserved LoadBalancer IP range (outside VIPs) |
| Git branch | `main` | Branch ArgoCD tracks for this cluster's manifests |
| Per-node: hostname | `spoke1-cp1` | Short hostname; `cp` prefix convention for control-plane nodes |
| Per-node: static IP | `192.168.2.10` | Within machine network; reserved in DHCP if applicable |
| Per-node: BMC IP | `192.168.0.21` | Out-of-band management address |

> **Network isolation:** `cluster_network_cidr` and `service_network_cidr` must
> be unique across all clusters in the fleet. The pre-flight CIDR conflict check
> (Step 0 of the pipeline) validates this automatically against all existing
> `vars/clusters/*.yml` files.

Create the cluster definition file from the provided example:

```bash
cp vars/clusters/spoke1.yml vars/clusters/<cluster-name>.yml
```

> **Naming convention:** name the file `<cluster.name>.yml`, matching the stem
> to the `cluster.name` value defined inside the file. The pipeline play header
> and CIDR preflight loop labels are derived from the filename, while CIDR
> conflict error messages are derived from `cluster.name`. Keeping them aligned
> makes pipeline log output self-consistent and makes the `vars/clusters/`
> directory scannable at a glance. A mismatch does not cause a pipeline failure,
> but produces a confusing asymmetry in log output during troubleshooting.

## 4. Run the Onboarding Pipeline

Once the cluster definition file is complete, the pipeline handles everything:
hardware discovery, manifest generation, Git operations, Vault secret loading,
ArgoCD sync, and BMC-controlled cluster installation boot.

```bash
cd ansible
ansible-playbook playbooks/cluster_onboard.yml \
  -e cluster_config=vars/clusters/<cluster-name>.yml \
  --ask-vault-pass
```

The pipeline completes when the spoke nodes have booted from the Assisted
Installer discovery ISO and begun registering with ACM. Cluster installation
then proceeds autonomously (45–90 minutes depending on hardware).

For full pipeline documentation including Git commit strategy, ArgoCD sync
strategy, Vault sequencing, and all configurable variables, see
[Cluster Onboarding Pipeline](cluster-onboarding-pipeline.md).

## 5. Monitor Provisioning

Watch agents register as nodes boot from the discovery ISO:

```bash
# Agents appear as each node boots — one Agent per node
watch oc get agents -n <cluster-name>

# When all agents show Approved/Bound, installation begins automatically
oc get agentclusterinstall <cluster-name> -n <cluster-name> \
  -o jsonpath='{.status.conditions}' | python3 -m json.tool

# Stream installation progress events
oc get events -n <cluster-name> \
  --sort-by='.lastTimestamp' | tail -30

# Watch ClusterDeployment transition to installed: true
watch oc get clusterdeployment <cluster-name> -n <cluster-name>
```

Full installation typically takes 45–90 minutes after all agents register.

## 6. Verify the Managed Cluster

```bash
# Cluster appears in ACM when installation completes
oc get managedcluster <cluster-name>

# Retrieve the admin kubeconfig
oc get secret <cluster-name>-admin-kubeconfig \
  -n <cluster-name> \
  -o jsonpath='{.data.kubeconfig}' | base64 -d > /tmp/<cluster-name>.kubeconfig

# Verify nodes — all should show Ready
KUBECONFIG=/tmp/<cluster-name>.kubeconfig oc get nodes

# Verify cluster operators — all should show Available=True
KUBECONFIG=/tmp/<cluster-name>.kubeconfig oc get clusteroperators

# Verify the GitOps bootstrap policy applied the GitOps operator
KUBECONFIG=/tmp/<cluster-name>.kubeconfig \
  oc get subscription openshift-gitops-operator \
  -n openshift-operators
```

## 7. GitOps for the Spoke Cluster

The `gitops-bootstrap-policy` (wave 15 on the hub) installs the OpenShift
GitOps operator on every managed cluster automatically once ACM marks it
Available. After that, workloads can be delivered to the spoke through either
the centralized or decentralized model.

For a full discussion of the trade-offs, operational considerations, and
decision guide for each model, see
[GitOps Delivery Models](gitops-delivery-models.md).

### Option A — Centralized (hub ArgoCD pushes to spoke)

The hub ArgoCD manages workloads on the spoke directly. Register the spoke as
an ArgoCD destination and add Applications that target it:

```bash
# Register the spoke cluster as an ArgoCD destination
argocd cluster add <cluster-name> \
  --kubeconfig /tmp/<cluster-name>.kubeconfig
```

Then add spoke-targeted Applications to `clusters/hub/values.yaml`:

```yaml
# In clusters/hub/values.yaml
  <cluster-name>-workloads:
    path: workloads/<cluster-name>
    syncWave: "25"
    destination:
      server: https://api.<cluster-name>.<base-domain>:6443
      namespace: default
```

### Option B — Decentralized (spoke ArgoCD pulls independently)

The spoke's own ArgoCD instance (deployed by the bootstrap policy) manages its
own workloads by pulling from this Git repository. Create a
`clusters/<cluster-name>/values.yaml` with the spoke-specific applications and
point the spoke's root Application at `clusters/<cluster-name>`:

```yaml
# clusters/<cluster-name>/values.yaml
applications:
  <cluster-name>-operators:
    path: workloads/<cluster-name>/operators
    syncWave: "5"
    destination:
      namespace: openshift-operators
```

The spoke ArgoCD root Application should point at `clusters/<cluster-name>` in
this repository, tracking the branch pinned in `clusters/cluster-versions.yaml`
for this cluster.
